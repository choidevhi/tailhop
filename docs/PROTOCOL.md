# TailHop 프로토콜 v1

Tailscale 망 위에서 PC(Windows)와 폰(Android), 또는 PC와 PC가 텍스트·파일을 주고받는다.
PC ↔ PC는 PC 앱 1.4.0에서 더한 **v1 확장**이다. 선(wire) 형식·헤더 `v`는 그대로 1이고, 폰 쪽은 바뀐 것이 없다(§8).
**이중 잠금**: (1) Tailscale WireGuard 암호화 + 기기 인증, (2) 페어링으로 나눈 비밀키로 모든 메시지를 AES-256-GCM 암호화·인증.

## 1. 네트워크
- PC는 TCP `47100`, 폰은 TCP `47101`에서 대기한다. PC끼리는 서로 상대의 `47100`으로 보낸다.
- **자기 Tailscale IPv4(100.64.0.0/10)에만 bind** 한다. `0.0.0.0` 금지. 와이파이/LAN에서는 보이지 않는다.
- 접속 허용: 상대 IP가 페어링된 기기 IP와 같아야 한다. PC는 추가로 `tailscale whois --json <ip>`의 사용자 로그인이 PC 자신의 사용자와 같은지 확인한다.
  - 태그 노드(whois의 `Node.Tags`가 비어 있지 않음)는 PC가 페어링·메시지 모두 거부한다(1.5.0). 태그 노드는 사람 계정이 아니라 공용 "tagged-devices" 사용자로 묶여 UserID 비교로는 내 기기인지 알 수 없다. 이 PC 자신이 태그 노드면 다른 기기와 연결되지 않는다.
- 동시 접속 최대 4개, 소켓 무응답 30초면 끊는다.
  - (1.5.0) 연결을 받자마자, 슬롯을 잡기 전에 상대 IP가 페어링된 기기이거나 페어링 창이 열려 있는지 본다. 아니면 아무것도 읽지 않고 닫는다(whois도 돌리지 않음). Android는 처음부터 이 순서였다.
  - (1.5.0) PC는 인증 전(머리 22바이트, 페어링 첫 프레임) 무응답 한도를 5초로 줄이고, 인증(whois·페어링 키 첫 프레임)이 끝나면 30초로 늘린다.
- 수신 중지(PC·Android 1.5.0): 대기 소켓을 닫아 포트 자체를 닫는다(Android는 수신 서비스를 멈춘다). 보내는 쪽은 연결 거부·시간 초과를 받는다. 이미 연결된 받기는 끝까지 받고, 중지 중에도 보내기는 된다. PC는 중지 중에 페어링 창을 열지 않는다.

## 2. 키
- 장기 비밀 `S` (32바이트 난수, 페어링 때 폰이 생성).
- 방향 키: `K_dir = HKDF-SHA256(ikm=S, salt=32바이트 0, info, L=32)`
  - 폰→PC: info = `"tailhop v1 phone->pc"`
  - PC→폰: info = `"tailhop v1 pc->phone"`
  - 페어링: ikm = QR의 `P`, info = `"tailhop v1 pair"`
  - PC ↔ PC (§8): 코드를 보여 준 PC = host, 입력한 PC = joiner
    - joiner→host: info = `"tailhop v1 pc-joiner->pc-host"`
    - host→joiner: info = `"tailhop v1 pc-host->pc-joiner"`
  - 다섯 info가 모두 달라서 한 `S`에서 나온 키라도 방향·기기 종류가 다르면 절대 같은 키가 되지 않는다. 연결마다 새 salt로 세션 키를 만들고, 한 연결 안에서는 nonce의 `dir` 바이트로 두 방향을 나눈다.
- 저장: PC는 Windows DPAPI(CryptProtectData)로, 폰은 Android Keystore AES 키로 감싸서 저장한다. 평문 저장 금지. PC의 설정·페어링·기록 파일은 상속을 끊고 현재 사용자만 접근하는 ACL로 쓴다(1.5.0, ACL을 지원하지 않는 디스크면 기본 ACL 그대로).
- 확인 코드: `SHA-256(S)` 앞 4바이트를 big-endian 정수로 읽고 `% 1000000`, 6자리 0채움. 양쪽 화면에 표시.

## 3. 연결 형식 (보내는 쪽 = 클라이언트)
1. 평문 22바이트: `"THP1"`(4) + kind(1: `0x01` 페어링, `0x02` 메시지) + salt(16, 난수) + 예약 `0x00`(1)
2. 세션 키 `SK = HMAC-SHA256(key=K_dir, msg=salt)` (32바이트, AES-256 키)
3. 프레임: `len`(4바이트 big-endian, 암호문+태그 길이) + 암호문. `len`은 16 이상 `1048576+16` 이하. 벗어나면 즉시 끊는다.
4. nonce(12바이트) = `dir`(1) + `index`(10바이트 big-endian) + `last`(1)
   - `dir`: 클라이언트→서버 `0x00`, 서버→클라이언트 `0x01`
   - `index`: 방향별 0부터 1씩 증가
   - `last`: 마지막 프레임이면 `0x01`, 아니면 `0x00`
   - AAD: 22바이트 평문 머리 전체
5. 클라이언트 프레임 0 = 헤더 JSON(UTF-8), `last=0`. 프레임 1..n = 파일 데이터(평문 최대 1 MiB), **마지막 데이터 프레임은 `last=1`** (빈 평문 가능). 텍스트·페어링도 헤더 뒤에 빈 `last=1` 프레임 하나를 보낸다. `last=1`을 받기 전에 끊기면 전부 버린다.
6. 서버 응답: `dir=0x01, index=0, last=1` 프레임 하나, JSON `{"ok":true}` 또는 `{"ok":false,"error":"...","code":"..."}`.
   - `error`: 사람이 읽는 한국어 문장. 1.4 이하 PC·Android 1.3 이하가 화면에 그대로 띄우므로 화면 언어와 상관없이 늘 한국어로, 예전과 같은 문장을 보낸다.
   - `code`(1.5.0에서 더함, 없을 수 있음): 언어와 상관없는 고정 코드(`[a-z_]{1,40}`, §10). 받는 쪽은 아는 코드면 자기 화면 언어 문장으로 바꿔 보여 주고, 모르거나 없으면 `error`를 200자까지 그대로 보여 준다.
   - GCM 태그 검사에 실패하면 응답 없이 끊는다. 거부 응답을 보낸 쪽은 상대가 이미 보낸 프레임을 조금 읽어 버린 뒤 닫는다(안 읽은 데이터가 남은 채 닫으면 RST로 응답이 사라질 수 있다).

## 4. 헤더 JSON
공통: `{"v":1,"type":"text"|"file"|"pair"|"unpair","id":"<32자 hex 난수>","ts":<유닉스 ms>,"from":"<보낸 기기 이름>"}`
- `from`·응답 `name`은 받는 쪽이 제어문자와 bidi·폭 없는 문자(§5와 같은 목록)를 지우고 64자로 자른다.
- unpair (1.5.0, v1 확장, 폰 → PC): 본문 없이 헤더 뒤 빈 `last=1` 프레임 하나. 페어링 취소(§6). PC 1.5.0+는 그 기기의 페어링과 기록을 지운 뒤 `{"ok":true}`로 답한다. 이전 PC는 `unsupported`로 거부하며, 폰은 결과를 무시한다.
- text: `"text": "<문자열>"` (UTF-8 최대 1 MiB)
- file: `"name": "<파일명>"`, `"size": <바이트>` (최대 4 GiB)
- pair: `"secret": "<S base64url, 패딩 없음>"`, `"port": 47101` — 응답에 `"name": "<PC 이름>"`
  - PC가 페어링할 때만 `"device": "pc"`, `"port": <자기 대기 포트>`를 더 넣는다. `device`가 없으면 폰이다. `"phone"`/`"pc"` 외 값은 거부한다.

## 5. 받는 쪽 검사 (하나라도 실패하면 거부·삭제)
- 매직/kind/길이 검사, GCM 태그 검사(실패 즉시 끊음).
- `|ts - now| <= 300000ms`, 최근 10분 내 본 `id`면 거부(재전송 공격 방지, 디스크에 보관).
- 파일: 받은 바이트 수 == `size`(정수, bool 아님). `.part` 임시 파일을 배타적으로 만들어 받고 검증 후 이름 변경. 다른 수신이 같은 이름의 `.part`를 먼저 만들었으면 다음 번호를 쓰고, 실패해도 자기가 만든 `.part`만 지운다.
- 디스크 여유(1.5.0): 받기 전에 `size + 64 MiB`보다 남은 공간이 적으면 `disk_full`로 거부한다(PC는 저장 폴더의 디스크, Android는 공용 저장소).
- 파일명 정리: 경로 성분 제거(마지막 `/` `\` 뒤만), 다음 문자 → `_`: C0 제어문자, `0x7F–0x9F`, bidi·보이지 않는 문자(`U+061C`, `U+200B`, `U+200E–200F`, `U+202A–202E`, `U+2060–2064`, `U+2066–206F`, `U+FEFF`, 1.5.0), `<>:"/\|?*`. 앞의 `.`과 끝의 공백·`.` 제거, 최대 150자(확장자 유지), 비면 `file`. 첫 `.` 앞부분의 끝 공백을 뗀 값이 Windows 장치 이름(CON, PRN, AUX, NUL, CONIN$, CONOUT$, COM0–9, LPT0–9, COM¹²³, LPT¹²³, 대소문자 무관)이면 앞에 `_`(예: `COM1 .txt` → `_COM1 .txt`). 같은 이름이 있으면 `이름 (1).확장자`. 글자를 잇는 ZWJ/ZWNJ(`U+200C–200D`)는 그대로 둔다.
- 받은 파일은 절대 자동 실행하지 않는다.

## 6. 페어링
1. PC에서 "기기 연결" → `P` 32바이트 난수 생성, QR 표시(120초, 1회용):
   `tailhop://pair?v=1&h=<PC tailscale IP>&p=47100&n=<PC 이름, URL 인코딩>&k=<P base64url>`
2. 폰이 QR을 스캔 → `S` 생성 → kind `0x01`로 접속, 페어링 키로 암호화한 `type:"pair"` 헤더 전송.
3. PC: 페어링 창이 열려 있고, whois 사용자가 같고 태그 노드가 아니면 `S`, 폰 IP, 이름, 포트를 저장하고 창을 닫는다(`P` 폐기). `P`를 1회용으로 쓰는 순간 120초 마감을 다시 확인한다(받는 동안 지났으면 거부). `port`는 1–65535 정수(bool 아님). QR이 나중에 유출돼도 `S`는 모른다.
4. 양쪽에 확인 코드를 표시한다. 다시 페어링하면 이전 정보를 덮어쓴다.
5. (Android 1.5.0) 폰은 PC의 `ok` 응답을 받아도 **바로 저장하지 않는다.** QR만으로는 그 기기가 내 PC인지 알 수 없으므로(같은 tailnet의 다른 기기가 보여 준 QR일 수 있다) 확인 코드와 PC 이름·주소를 보여 주고 "PC에 표시된 코드와 같나요?"를 묻는다.
   - 같다: 그때 저장한다. 다른 기기가 이미 있으면 기본 공유 대상은 바꾸지 않는다(대화방을 열거나 공유 확인 창에서 고를 때만 바뀐다).
   - 다르다: `S`를 지우고, 그 `S`로 `type:"unpair"` 메시지(§4)를 보내 PC에도 지우게 한다(실패해도 폰은 저장하지 않았으므로 무시).
   - 선(wire) 형식은 그대로다. PC 쪽 동작(창·whois·저장)도 같다.

## 7. 테스트 벡터
`docs/test_vectors.json` 참고(같은 입력이면 양쪽 구현의 출력이 바이트 단위로 같아야 한다).

## 8. PC ↔ PC (v1 확장, PC 앱 1.4.0)
카메라가 없으므로 QR 대신 링크나 코드를 옮겨 적는다. 검사는 폰 페어링과 같고 더 줄인 것은 없다.
1. host PC가 "새 기기 연결"을 열면 폰용 QR과 함께 같은 창(같은 `P`, 120초, 1회용)의 두 형태를 보여 준다.
   - 링크: QR과 같은 `tailhop://pair?v=1&h=…&p=…&n=…&k=…` (매개변수를 더하지 않는다. 안드로이드 QR 검사가 그대로 통과하도록)
   - 짧은 코드: `<host IPv4>[:<port>]-XXXXX-XXXXX-…` — `P`(32바이트) + 검사 2바이트(`SHA-256("tailhop pair code|<host>:<port>|" + P)` 앞 2바이트)를 Crockford base32(`0-9A-Z`에서 I L O U 제외)로 적고 5글자씩 끊는다. 포트가 47100이면 생략. 대소문자·공백·하이픈 무관, `O→0`, `I/L→1`로 읽는다. 키 강도는 QR과 같은 256비트이고 검사 바이트는 오타(주소 포함)를 미리 잡는 용도다.
2. joiner PC는 입력을 엄격히 검사하고, host 주소가 Tailscale IPv4인지, `whois`로 같은 사용자의 기기인지, 자기 자신이 아닌지 **보내기 전에** 확인한다.
3. joiner가 `S`를 만들고 kind `0x01`로 접속해 `type:"pair"`, `device:"pc"`, `port`를 보낸다. host는 폰과 똑같이 창 열림·whois 같은 사용자·재전송·1회용을 검사하고, 추가로 자기 자신(같은 Tailscale 기기 ID)은 거부한다.
4. host는 상대를 `pc/host`로, joiner는 응답(인증된 `name`)을 받은 뒤 상대를 `pc/joiner`로 저장한다. 양쪽에 같은 확인 코드(§2)를 보여 준다. 다시 페어링하면 같은 기기(Tailscale 기기 ID)의 기존 정보를 덮어쓰며, 이때 역할이 바뀔 수 있다.
5. 메시지는 §3 그대로이며 방향 키만 §2의 PC ↔ PC info를 쓴다. 받는 쪽 검사(§1 IP·whois·기기 ID, §5)는 폰과 같다.

## 9. PC 저장 형식
`pairings.json` 항목: `ip`, `port`, `name`, `stable_id`, `kind`(`phone`|`pc`), `role`(폰은 `""`, PC는 `host`|`joiner`), `secret_dpapi`.
1.2 이하의 `phone_ip`/`phone_port`/`phone_name`/`phone_stable_id` 형식은 처음 읽을 때 `kind:"phone"`으로 옮긴다. 1.5.0 이전에 남기던 원본 사본 `pairings.json.v1.bak`(해제한 기기의 비밀까지 담김)은 새 형식을 제대로 읽으면 지운다. 기기 표시가 없는 예전 기록은 첫 폰의 대화로 옮겨 저장한다.
연결 해제(PC 1.5.0): 페어링과 함께 그 기기와 주고받은 기록(`texts/`의 긴 글 포함)도 지운다(Android와 같음). 받은 파일 자체는 지우지 않는다.

`settings.json`(1.5.0): `language`(`system`|`ko`|`en`|`ja`|`zh_CN`), `receiving`(기본 true), `pause_until`(유닉스 초, 시간을 정해 멈췄을 때만), `hotkey`(1.6.0, 전역 단축키를 켰을 때 true), `previews`(1.6.1, 미리보기를 껐을 때만 false), `cloud`(1.8.0, 클라우드 모드를 켰을 때 true), `cloud_dir`(클라우드 폴더, 없으면 `%USERPROFILE%\TailHop Cloud`), `cloud_collect`(대화방으로 받은 파일도 클라우드에 모을 때 true).

`outbox.json`(1.7.0): 보낼 곳 목록. 작업마다 `id`(16자 hex), 종류(`text`|`file`|`folder`|`cloud_put`|`cloud_get`), 받을 기기, 글 또는 경로, `xfer`, 시도 횟수·다음 시각·상태. 읽을 때 형식이 틀린 항목은 버린다. 묶은 zip·클립보드 이미지·가져오는 중인 조각은 `outbox/<id>/`에 두고 끝나면 지운다. `resume.json`(1.7.0): 받다 만 조각과 끝난 `xfer`(상대 기기별, 24시간).

`bridge.json`(PC 1.6.0): 명령줄·탐색기 '보내기' 메뉴가 실행 중인 앱에 보내기를 맡기는 로컬 소켓(`127.0.0.1`)의 `port`, `token`(32바이트 hex), `pid`. 이 사용자만 읽는 ACL로 쓰고 앱이 끝나면 지운다. 요청은 JSON 한 줄(`token`, `paths`, `text`, `to`, `list`)이고 토큰이 틀리면 답하지 않는다. 기기 사이 선(wire) 형식과는 상관없다. 폴더는 `<폴더 이름>.zip`으로 묶어 보통 파일(§4 `file`)로 보낸다(링크는 따라가지 않는다).

기록(1.5.0): 2000자보다 긴 텍스트는 `texts/<32자 hex>.txt`에 따로 두고 `history.json` 항목에는 앞 2000자(`text`), 파일 이름(`text_file`), 전체 글자 수(`text_len`)만 남긴다. 1.4 이하 기록은 처음 열 때 한 번 옮긴다. 항목이 잘리거나 지워지면 그 파일도 지운다. Android는 같은 방식으로 `files/texts/<id>.txt`와 `tlen`을 쓴다.

## 10. 오류 코드 (응답의 `code`)
받는 쪽(응답을 보내는 쪽)이 쓰는 코드. 한국어 `error` 문장은 1.4와 같다.
| code | 뜻 |
|---|---|
| `no_body` | 헤더 뒤에 본문 프레임이 없다 |
| `bad_header` | 헤더 JSON을 읽을 수 없다 |
| `unsupported` | `v`·`type`을 지원하지 않는다 |
| `clock_skew` | `ts`가 ±5분을 벗어났다 |
| `bad_id` | `id` 형식이 잘못되었다 |
| `replay` | 최근 10분 안에 본 `id`다 |
| `bad_text` / `bad_text_format` | 텍스트가 잘못되었다 / 텍스트 뒤 프레임이 규칙과 다르다 |
| `bad_file_info` | `name`·`size`가 잘못되었다 |
| `file_too_big` / `file_incomplete` | 알린 크기보다 크다 / 덜 왔다 |
| `after_last` / `bad_frame_len` | 마지막 프레임 뒤 데이터 / 프레임 길이 위반 |
| `storage` / `storage_permission` / `storage_folder` / `storage_denied` | 저장 실패(PC도 1.5.0부터 `.part`를 만들 수 없을 때) / 저장 권한 없음(Android 8–9) / 저장 폴더를 만들 수 없음 / 저장소 접근 거부 |
| `disk_full` | (1.5.0) 받을 디스크 공간이 부족하다(§5) |

`tagged_node`(1.5.0)는 응답 코드가 아니라 화면용 코드다. PC는 태그 노드를 인증 전에 응답 없이 끊는다.

## 11. 전송 신뢰성 확장 (1.7.0, v1 확장)
선(wire) 형식(§3)과 헤더 `v:1`은 그대로다. 새 메시지 `hello`와 헤더 필드 `xfer`·`offset`을 더한다. 1.6 이하 PC·1.5 이하 Android는 `hello`를 `unsupported`로 거부하므로, 보내는 쪽은 그때 예전 방식(§4 `file`, `xfer` 없음)으로만 보낸다.

### 11.1 hello (능력 확인·이어받기 위치)
- 요청: `{"v":1,"type":"hello","id","ts","from"}` + 선택 `"xfer":"<32자 hex>","size":<정수>` 뒤에 빈 `last=1` 프레임 하나.
- 응답: `{"ok":true,"caps":["xfer","cloud"],"cloud":<bool>,"have":<정수>,"done":<bool>}`
  - `caps`: 이 기기가 아는 확장. `"xfer"` = §11.2, `"cloud"` = §12를 안다. 모르는 값은 무시한다.
  - `cloud`: 지금 클라우드 모드가 켜져 있는지(§12).
  - `have`: `xfer`를 줬을 때, 그 상대(보낸 기기)·`xfer`·`size`가 모두 같은 받다 만 조각의 길이. 없으면 0.
  - `done`: 그 `xfer`를 최근 24시간 안에 끝까지 받았으면 true(보내는 쪽은 다시 보내지 않고 보낸 것으로 친다).
- `hello`는 받는 쪽 상태를 바꾸지 않는다(재전송 검사 §5는 그대로 거친다).

### 11.2 xfer (재시도·이어받기·무결성)
보내는 쪽은 보내기 한 건마다 `xfer`(32자 hex 난수)를 정하고, 그 건을 다시 보낼 때(재시도) 같은 값을 쓴다. 상대가 `hello`에서 `"xfer"`를 알린 뒤에만 쓴다.
- **text**: 헤더에 `"xfer"`를 더한다. 받는 쪽은 최근 24시간 안에 같은 상대·같은 `xfer`의 글을 이미 받았으면 다시 기록·알림하지 않고 `{"ok":true}`로 답한다(응답이 사라져 다시 보낸 경우).
- **file**: 헤더에 `"xfer"`, `"offset":<정수, 0 ≤ offset ≤ size>`를 더한다.
  - 데이터 프레임은 파일의 `offset`부터 끝까지 `last=0`으로 보낸다(평문 최대 1 MiB, 빈 데이터 프레임 금지).
  - 그 뒤 **트레일러** 프레임 하나를 `last=1`로 보낸다: `{"sha256":"<파일 전체의 SHA-256, 64자 hex>"}`.
  - 받는 쪽: `offset > 0`이면 같은 상대·`xfer`·`size`의 조각이 있고 그 길이가 `offset` 이상이어야 한다. 조각을 `offset` 길이로 자르고 이어 쓴다. 없으면 `resume_lost`로 거부한다(보내는 쪽은 `hello`를 다시 해서 처음부터 보낸다).
  - 받은 바이트 합(`offset` + 이번 데이터)이 `size`와 같아야 하고, 조각 전체의 SHA-256이 트레일러와 같아야 한다. 다르면 조각을 지우고 `hash_mismatch`로 거부한다.
  - 끊기거나 시간 초과로 멈추면 받는 쪽은 조각(`.part`)을 **지우지 않고** 24시간 동안 둔다. 규칙 위반(§5)·`hash_mismatch`·디스크 부족이면 지운다. 24시간 지난 조각은 지운다.
  - 디스크 여유 검사(§5)는 `size - offset + 64 MiB`로 한다.
  - 이미 끝난 `xfer`(`done`)를 다시 `offset:0`으로 받으면 새로 받는다(보내는 쪽이 `hello`의 `done`을 보고 건너뛰어야 한다).
- 받는 쪽 기록: 조각과 끝난 `xfer`는 상대 기기 ID(PC는 Tailscale StableID, Android는 PC IP)별로 따로 센다. 다른 상대가 같은 `xfer`를 말해도 남의 조각을 쓰지 않는다.

### 11.3 재시도 규칙 (보내는 쪽)
- 보내기는 **보낼 곳 목록(outbox)** 에 넣고 기기마다 차례로 보낸다. 한 기기가 꺼져 있어도 다른 기기로의 보내기는 막히지 않는다.
  - (1.8.0) 기기마다 줄이 둘이다: 대화방(text·file)과 클라우드(§12의 올리기·가져오기). 줄 안에서는 넣은 순서를 지키고, 두 줄은 함께 돈다(큰 클라우드 받기가 대화방 글을 막지 않게).
- 다시 시도하는 실패: 연결 실패·거부, 시간 초과, 응답 전 끊김, `resume_lost`, `hash_mismatch`(처음부터), 보내는 중 파일이 바뀜(새 `xfer`로 처음부터). 간격은 3초, 10초, 30초, 1분, 2분, 그 뒤 5분마다. 24시간 동안 못 보내면 실패로 둔다. 상대에게서 메시지가 오면(상대가 켜졌다) 그 기기의 대기를 바로 깨운다.
- 다시 시도하지 않는 실패: 상대가 이유와 함께 거부함(§10의 코드, 위 둘 제외), 보낼 파일이 사라짐, 페어링 해제. 화면에 실패로 보이고 사용자가 다시 보낼 수 있다.
- 파일이 대기 중에 바뀌면(크기 또는 수정 시각) 새 `xfer`로 처음부터 보낸다.
- PC는 연결에 실패하면 `tailscale status`에서 그 기기(StableID)의 지금 주소를 찾아 바뀌었으면 페어링의 주소를 고친다.

### 11.4 오류 코드 추가
| code | 뜻 |
|---|---|
| `resume_lost` | 이어 받을 조각이 없다(처음부터 다시) |
| `hash_mismatch` | 다 받았는데 SHA-256이 다르다 |
| `bad_xfer` | `xfer`·`offset`·트레일러 형식이 잘못되었다 |

### 11.5 꺼진 상대 기다리기 (2.2.0)
- 상대가 꺼져 있으면(연결 거부·시간 초과·Tailscale 꺼짐) 보낼 곳 목록에 그대로 두고, 30일이 지날 때까지(그 전에는 사용자가 취소할 때까지) 기다린다(2.1까지는 24시간). 다시 시도 간격은 §11.3과 같고, 아래 신호가 오면 바로 깨운다.
- **켜졌다 알리기**: 받기를 열 때마다(앱을 켬, Tailscale이 다시 붙음, 수신 중지를 풂) 연결된 기기마다 §11.1 hello를 한 번 보낸다(같은 기기에 60초에 한 번까지). 받는 쪽은 어떤 메시지든(hello 포함) 받으면 그 기기로 가려고 기다리던 것을 바로 보낸다.
- **PC**: 꺼진 상대를 기다리는 건이 있을 때만 30초마다 Tailscale 상태(`tailscale status`의 Online)를 보고, 켜졌으면 바로 깨운다. 기다리는 건이 없으면 묻지 않는다.
- **Android**: 기다리는 동안 보내기 서비스(포그라운드)를 끄고, 시스템 예약 작업(JobScheduler, 네트워크 연결 조건, 15분 이상 간격)과 네트워크·Tailscale 연결 변화, 상대의 메시지로만 다시 시도한다(배터리).

## 12. 클라우드 모드 (1.8.0, v1 확장)
클라우드 모드를 켠 기기(이하 **허브**)는 자기 안의 클라우드 폴더를 페어링된 모든 기기에 연다. 다른 기기는 그 폴더를 보고, 가져오고, 올리고, 지울 수 있다. 꺼져 있으면 아래 요청은 모두 `cloud_off`로 거부한다. 페어링·인증·재전송 검사(§1–§5)는 그대로다.
- 폴더: PC 기본 `%USERPROFILE%\TailHop Cloud`(설정에서 바꿈), Android `Download/TailHop/Cloud`(MediaStore, 이 앱이 만든 파일만 보인다).
- 대화방으로 받은 파일은 평소처럼 저장 폴더로 간다. 설정 "받은 파일도 클라우드에 모으기"를 켜면 클라우드 폴더 맨 위에 저장한다.

### 12.1 경로
- 클라우드 안의 위치는 `/`로 나눈 상대 경로 문자열이다. 빈 문자열 = 맨 위.
- 각 조각은 비어 있지 않고, `.`·`..`이 아니며, §5 파일명 정리를 거쳐도 그대로인 이름이어야 한다. 조각 16개, 전체 1024자까지. 앞뒤 `/`, 겹친 `//`, `\` 금지. 어기면 `bad_path`.
- 허브는 경로를 클라우드 폴더 아래로 풀고, 실제 위치가 클라우드 폴더 안인지 다시 확인한다. 중간에 링크(심볼릭 링크·정션·재분석 지점)가 있으면 따라가지 않고 `bad_path`.
- 이름이 `.part`로 끝나거나(대소문자 무관) 숨김·시스템 파일이거나 위 조각 규칙에 맞지 않으면(허브에서 직접 넣은 이상한 이름) 목록에 보이지 않고 요청도 `not_found`. 중간 폴더가 숨김이어도 같다.
- 허브는 요청한 이름이 디스크의 실제 이름과 같은지 확인한다. Windows의 8.3 짧은 이름(`ENV~1`)이나 대소문자만 다른 별칭으로 숨긴 이름을 열지 못한다.

### 12.2 메시지 (모두 kind `0x02`, 헤더 뒤 빈 `last=1` 프레임, 단 `cloud_put`은 §11.2 파일과 같음)
- `cloud_list`: `{"path":"<폴더>","cursor":<정수, 선택>}` → 응답 `{"ok":true,"items":[{"name","dir":<bool>,"size":<정수>,"mtime":<유닉스 ms>}...],"next":<정수|null>}`. 한 번에 500개, 폴더 먼저, 이름순(대소문자 무시). `next`가 있으면 그 값을 `cursor`로 다시 묻는다.
- `cloud_get`: `{"path":"<파일>","offset":<정수>,"size":<정수, 선택>,"mtime":<정수, 선택>}` → 서버가 먼저 `{"ok":true,"size","mtime"}`를 `dir=1, last=0` 프레임으로 보내고, 이어서 `offset`부터 끝까지 데이터 프레임(마지막 데이터 프레임 `last=1`, 빈 평문 가능)을 보낸다. `size`·`mtime`을 줬는데 지금 파일과 다르면 `cloud_changed`(이어받기 중 파일이 바뀜). 이 검사를 `offset` 범위 검사보다 먼저 한다(파일이 줄었으면 처음부터 다시 받게). 거부는 §3 응답 한 프레임(`last=1`).
  - 허브는 첫 `ok` 프레임을 보낸 뒤 읽기 오류가 나면 거부 응답을 보내지 않고 연결만 끊는다(가져오는 쪽이 거부 문장을 데이터로 읽지 않게). 가져오는 쪽은 `last`까지 받았는데 크기가 모자라면 조각을 버린다.
  - 가져오는 쪽은 `.part`로 받고, 끊기면 `size`·`mtime`과 함께 조각을 두었다가 `offset`으로 이어 받는다.
- `cloud_put`: §11.2 `file`과 같고 헤더에 `"dir":"<올릴 폴더>"`를 더한다(없는 폴더는 만든다). 같은 이름이 있으면 `이름 (1).확장자`. 이름이 `.part`로 끝나면(대소문자 무관) 끝에 `_`를 붙이고, 140자로 미리 줄여(확장자는 남김) 저장한다. 같은 이름이 있어 번호가 붙어도 §12.1 규칙을 지켜 모든 기기에서 보이고 지울 수 있게 하려는 것이다. "받은 파일도 클라우드에 모으기"로 클라우드에 저장하는 대화방 파일도 같다. 응답 `{"ok":true,"name":"<저장된 이름>"}`. `xfer`·트레일러는 필수다.
  - 받다 만 조각은 메시지 종류(`file`/`cloud_put`)와 받을 폴더까지 같을 때만 이어 받는다. 클라우드를 끄거나 폴더를 바꾸면 클라우드 쪽 조각을 지운다.
- `cloud_del`: `{"path":"<파일 또는 폴더>"}` → 지운다. PC는 휴지통으로 보낸다(폴더는 안의 것까지). Android는 이 앱이 만든 파일만 지운다. 맨 위(빈 경로)는 지울 수 없다(`bad_path`).
- `cloud_mkdir`: `{"path":"<새 폴더>"}` → 만든다(이미 있으면 그대로 성공).

### 12.3 오류 코드 추가
| code | 뜻 |
|---|---|
| `cloud_off` | 이 기기는 클라우드 모드가 꺼져 있다 |
| `bad_path` | 경로가 규칙(§12.1)에 맞지 않는다 |
| `not_found` | 그런 파일·폴더가 없다 |
| `cloud_changed` | 이어 받는 사이 파일이 바뀌었다 |
| `cloud_denied` | 지울 수 없다(권한·사용 중) |

## 13. 업데이트 (1.9.0, v1 확장)
빌드한 PC(이하 **배포 PC**)가 새 설치 파일을 들고 있다가, 페어링된 다른 PC와 폰이 설정에서 바로 받아 설치한다. 오가는 길은 §3 그대로(Tailscale + 페어링 키)다. 인터넷·GitHub를 거치지 않는다.

### 13.1 배포 PC
- `%APPDATA%\TailHop\updates\manifest.json`과 같은 폴더의 파일이 있으면 배포 PC다. 빌드 스크립트(`windows\tools\publish_update.py`)가 설치 파일과 APK를 복사하고 manifest를 쓴다.
- manifest: `{"pc":{"version":"1.9.0","file":"TailHop_Setup_1.9.0.exe","size":<정수>,"sha256":"<64자 hex>"},"android":{"version":"1.9.0","code":9,"file":"TailHop-1.9.0.apk","size":<정수>,"sha256":"<64자 hex>"}}` (둘 중 하나만 있어도 된다).
- `file`은 폴더 안의 이름이어야 한다(경로 성분 금지, §5 파일명 정리를 거쳐도 같은 이름). manifest를 읽을 때 크기를 확인한다.
- hello 응답(§11.1)에 `"updates":{"pc":{"version","size"},"android":{"version","code","size"}}`를 더한다(있는 것만). `caps`에 `"update"`를 넣는다.

### 13.2 받기
- `update_get`: `{"target":"pc"|"android"}` + 빈 `last=1` 프레임 → 응답은 §12.2 `cloud_get`과 같은 모양이다. 먼저 `{"ok":true,"version","size","sha256"}`를 `last=0`으로, 이어서 파일 전체를 데이터 프레임으로(마지막 `last=1`). 없으면 `not_found`.
- 받는 쪽은 받은 크기와 SHA-256이 첫 프레임과 같은지 확인한다. 다르면 버린다(`hash_mismatch`).
- PC: 받은 설치 파일을 `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /RELAUNCH`로 실행한다. 설치 프로그램은 실행 중인 앱을 `--quit`으로 끄고 설치한 뒤 `/RELAUNCH`면 앱을 다시 켠다.
- Android: 받은 APK의 서명 인증서가 지금 앱과 같을 때만 PackageInstaller로 설치한다(다르면 `update_signer`). 처음 한 번은 시스템이 "이 앱에서 설치 허용"과 확인을 묻는다. 그 뒤로는 확인 없이 바로 바뀐다(Android 12+, TailHop이 설치한 앱일 때).
- 지금 버전보다 높을 때만 업데이트로 보인다(PC는 `version` 비교, Android는 `code` 비교).

## 15. 클라우드 미리보기·검색 (2.0.0, §12 확장)
허브의 hello `caps`에 `"cloud2"`가 있으면 아래를 쓴다. 없으면 예전 목록만 쓴다.
- `cloud_thumb`: `{"path":"<파일>","px":<64–512 정수>}` → 성공이면 `{"ok":true,"mime":"image/jpeg","w","h"}`(last=0) 뒤에 JPEG 데이터 프레임(마지막 last=1, 256 KiB 이하). 미리보기를 만들 수 없는 파일은 `not_found`. 허브는 사진·영상(§15 종류 image·video)만 만든다(잠긴 폴더 안은 사진만, 50 MB까지). 허브는 썸네일을 `%LOCALAPPDATA%\TailHop\thumbs`에 캐시한다(잠긴 폴더의 것은 캐시하지 않고 메모리에서만 만든다).
- `cloud_search`: `{"path":"<폴더>","query":"<0–100자>","kind":"all|image|video|audio|doc|archive|other","cursor":<정수>}` → `cloud_list`와 같은 모양의 응답이고, 항목마다 `"path"`(검색 시작 폴더 기준 상대 경로)를 더한다. 이름에 query가 들어 있는(대소문자 무시) 파일·폴더를 아래 폴더까지 찾는다. 한 번에 500개, 허브는 한 요청에 항목 50,000개·3초까지만 훑고 `"partial":true`를 붙일 수 있다. 숨김·`.part`·링크·잠긴 폴더 안은 건너뛴다(검색을 잠긴 폴더 안에서 시작했으면 그 열쇠로 그 안만 찾는다). `partial`은 훑다가 멈췄다는 뜻이고, 찾은 것이 500개를 넘으면 그와 상관없이 `next`가 있다.
- 종류는 확장자로 정한다(양쪽 구현이 같은 표를 쓴다, `docs/test_vectors.json`의 `file_kinds`).
- `cloud_list` 항목에 `"kind"`를 더한다(위 종류).

## 14. 잠긴 폴더 (2.0.0, §12 확장, PC 허브만)
클라우드 안의 폴더 하나를 잠그면 허브가 그 안의 파일을 암호화해 숨김 보관함(vault)으로 옮긴다. 허브의 탐색기에서는 암호문만 보이고, TailHop 앱에서 PIN을 넣어야 열린다. 암호화·복호화는 모두 허브가 한다(PIN은 §3의 암호 채널로 허브에 간다).
### 14.1 저장
- 보관함 폴더: `<클라우드>\.tailhop-vault\` (숨김·시스템 속성, 목록에 보이지 않음). `vaults.json`(평문): `{"vaults":[{"id":"<32 hex>","mount":"<클라우드 경로>","state":"locked|locking|unlocking"}]}`. `mount`는 잠근 폴더의 자리이고 그 이름은 목록에 그대로 보인다(내용·안의 이름은 안 보인다).
- 보관함마다 `<id>\vault.json`: `{"v":1,"kdf":"scrypt","n":32768,"r":8,"p":1,"salt":"<b64u 16B>","wrapped":"<b64u>","rsalt":"<b64u 16B>","rwrapped":"<b64u>"}`
  - 보관함 키 VK = 32바이트 난수. PIN 키 = scrypt(PIN UTF-8, salt, N, r, p, 32). PIN으로 감싼 값 = nonce(12) ‖ AES-256-GCM(PIN 키, VK, aad=`"tailhop vault v1|" + id`)이고, `wrapped`에는 그것을 허브 PC의 Windows 계정 보호(DPAPI, CurrentUser)로 한 번 더 감싼 것을 둔다. 디스크 사본만으로는 PIN을 맞혀 볼 수 없다(그 PC의 Windows 로그인이 필요하다). 복구 코드 키로 감싼 `rwrapped`는 DPAPI 없이 둔다(160비트라 맞힐 수 없고, Windows를 다시 깔아도 복구 코드로 열린다).
  - 복구 코드: 20바이트 난수를 Crockford base32로 쓰고 4글자씩 `-`로 끊는다(32글자). 잠글 때 한 번만 보여 준다. 허브는 받은 코드에서 영숫자만 남기고 대문자로 바꾼 뒤 `O→0`, `I/L→1`로 읽는다(사용자가 띄어 쓰거나 `-`를 빼도 된다).
- `<id>\index.bin`: nonce(12) ‖ AES-256-GCM(VK, JSON, aad=`"tailhop vault index|" + id`). JSON은 `{"entries":{"<보관함 안 상대 경로>":{"dir":<bool>,"size","mtime","obj":"<32 hex>"}}}`.
- `<id>\objects\<obj>`: 머리 `"THV1"`(4) ‖ 파일 nonce 접두(8) ‖ 크기(8, big-endian) 뒤에 1 MiB씩 자른 조각마다 AES-256-GCM(VK, 평문, nonce = 접두 ‖ 조각 번호(4, big-endian), aad = obj ‖ 조각 번호(4) ‖ 마지막이면 1 아니면 0(1)). 조각 하나 = 평문 + 태그 16. 조각 i의 자리를 계산해 원하는 위치부터 읽는다(이어받기).
### 14.2 잠그기·열기
- `cloud_lock`: `{"path":"<폴더>","pin":"<6–64자>"}` → 바로 `{"ok":true,"recovery":"<복구 코드>"}`로 답하고 허브가 뒤에서 파일을 하나씩 암호화한다. 하나를 보관함에 넣고 index를 쓴 다음에야 원본을 지운다(휴지통을 거치지 않음). 새로 들어온 파일도 다시 훑어 넣고, 끝에는 빈 폴더만 지운다(남은 것이 있으면 폴더째 지우지 않는다). 사용 중인 파일 때문에 다 못 넣으면 목록에 `"state":"stalled"`로 보이고, PIN으로 열면 이어 하고 `cloud_unlock`으로 되돌릴 수 있다. 앱이 꺼졌다 켜져도 같다. 그동안 그 폴더는 목록에 `"locked":true,"state":"locking","progress":<0–100>`으로 보인다. 잠그기 전에 만들어 둔 미리보기 캐시는 지운다. 맨 위 폴더, 이미 잠긴 폴더 안·위, 잠긴 폴더를 품은 폴더는 `bad_path`.
- `cloud_open`: `{"path":"<잠긴 폴더>","pin":"<PIN>"}` 또는 `{"path","recovery":"<코드>"}` → `{"ok":true,"token":"<32 hex>","ttl":1800}`. 틀리면 `vault_pin`. 보관함·기기마다 따로 세어(한 기기가 다른 기기를 막지 못하게) 5번 틀리면 60초, 그 뒤로는 틀릴 때마다 두 배(최대 1시간) 동안 `vault_wait`(`"retry":<초>`). 확인은 보관함마다 한 번에 하나씩 하고, 횟수는 확인 전에 올린다(동시에 넣어 횟수를 피하지 못하게).
- 열쇠(token)는 그 상대 기기에만 묶이고, 쓰일 때마다 30분 연장된다. 허브 앱이 꺼지면 모두 사라진다.
- 잠긴 폴더 안을 가리키는 §12·§15 요청(`cloud_list`·`get`·`put`·`del`·`mkdir`·`thumb`·`search`)은 헤더에 `"token"`을 더한다. 없거나 틀리면 `vault_locked`이고 응답에 `"mount":"<잠긴 폴더 자리>"`를 붙인다(어느 폴더의 PIN을 물을지). 잠긴 폴더 자리는 대소문자를 가리지 않고 비교한다. 잠긴 폴더 밖에서 시작한 `cloud_search`는 잠긴 폴더를 늘 건너뛴다.
- 허브는 요청 경로의 조각이 디스크의 실제 이름과 글자 하나까지 같을 때만 연다(대소문자 별칭·8.3 짧은 이름은 `not_found`). 앱은 목록에서 받은 이름을 그대로 쓴다.
- 잠긴 폴더 안으로 올리는 동안(`cloud_put`) `cloud_unlock`은 `vault_busy`다. 잠긴 폴더에 올라온 파일 이름은 허브의 알림에 쓰지 않는다.
- `cloud_unlock`: `{"path","pin"}` → 잠금을 풀어 평문 폴더로 되돌린다(뒤에서, `"state":"unlocking"`).
- `cloud_repin`: `{"path","pin"|"recovery","new_pin"}` → PIN을 바꾼다(VK는 그대로, `wrapped`만 다시). 그 보관함의 열쇠는 모두 끝난다.
- 잠긴 폴더 자체를 지우기(`cloud_del`)는 token이 있어야 한다. 보관함 폴더째 영구히 지운다.

## 16. 여러 항목 옮기기 (2.1.0, §12 확장)
허브의 hello `caps`에 `"move"`가 있으면 쓴다. 없으면 앱은 옮기기 메뉴를 숨긴다.
- `cloud_move`: `{"paths":["<파일 또는 폴더>", ...],"dest":"<옮겨 갈 폴더>"}` (+ 잠긴 폴더 안이면 §14.2 `"token"`) → `{"ok":true,"moved":[{"path":"<원래 경로>","name":"<옮긴 곳의 이름>"}...],"failed":[{"path":"<원래 경로>","code":"<오류 코드>"}...]}`.
  - `paths`는 1–200개(헤더가 한 프레임 1 MiB를 넘지 않게, 더 많으면 앱이 200개씩 나눠 보낸다), 각각 §12.1 규칙의 빈 경로가 아닌 경로. 같은 경로가 두 번 있으면 한 번만 옮긴다. 형식이 틀리면 요청 전체를 `bad_path`로 거부한다.
  - `dest`는 이미 있는 폴더여야 한다(없으면 `not_found`, 요청 전체 거부). 맨 위(빈 문자열)도 된다.
  - 항목마다 따로 옮기고, 안 된 것만 `failed`에 담는다(나머지는 옮긴다). 항목 오류: 없음 `not_found`, 자기 자신이나 자기 아래로 옮기기 `bad_move`, 사용 중 `cloud_denied`.
  - 이미 `dest` 안에 있는 항목은 그대로 두고 `moved`에 원래 이름으로 넣는다.
  - `dest`에 같은 이름이 있으면 `이름 (1).확장자`로 옮긴다(덮어쓰지 않는다).
  - 잠긴 폴더: 같은 보관함 안에서만 옮긴다. 잠긴 폴더 안팎을 오가거나, 잠긴 폴더 자체이거나, 잠긴 폴더를 품은 폴더면 그 항목은 `vault_move`(PIN으로 열고 받기·올리기로 옮긴다). 보관함 안끼리는 목록(index)만 바꾸고 암호문은 그대로다.
  - PC 허브는 같은 디스크 안에서 이름만 바꿔 옮긴다(복사하지 않는다).

## 17. 암호화 클라우드 저장소 (2.2.0, PC 허브)
PC 허브의 클라우드는 통째로 암호화 저장소다. 허브의 탐색기에는 알아볼 수 없는 조각만 보이고, 내용은 TailHop 앱(PC·폰)이 허브를 거쳐서만 연다. 위치는 허브 PC의 아무 드라이브·폴더(외장 SSD도)다. 암호 계산은 Google Tink(AEAD, AES-256-GCM)가 하고 비밀번호는 Argon2id(RFC 9106), 이 PC 묶기는 Windows DPAPI가 한다. 앱끼리 주고받는 모양(§12–§16)은 그대로이고 아래만 더하거나 바뀐다.

### 17.1 저장(허브 안, 참고용)
- 고른 폴더 안의 숨김 하위 폴더 `.tailhop-store` 하나만 쓴다. 같은 폴더의 다른 파일·폴더는 읽지도 지우지도 않고, 그 안에서도 링크·정션은 따라가지 않으며 정해진 이름(32자 hex)의 파일만 지운다. 평문 열에서 읽은 객체 이름도 늘 그 모양인지 확인한다.
- `store.json`: 표식·id, 비밀번호와 복구 코드로 각각 감싼 저장소 열쇠(Tink 암호화된 키 묶음). `meta.db`(SQLite): 항목마다 id·부모 id·열쇠 이름(ring)과 암호화된 meta(이름·크기·시각·파일 열쇠). `objects/`: 파일마다 새 Tink 열쇠로 1 MiB씩 따로 잠근 청크(연관 데이터 = 청크 번호·마지막 여부).
- 드러나는 것은 나무 모양(무엇이 무엇 아래 있는지)·개수·조각 크기와, 항목마다 딸린 버전의 개수·크기(그래서 사진·영상일 것은 짐작할 수 있다)뿐이다. 이름·시각·내용은 암호문이다. 받는 중 조각을 찾는 열은 xfer와 함께 해시해 기기 이름·크기를 평문으로 두지 않는다.
- 한계(알고 둔 것): 잠그기는 meta만 다시 잠그고 파일 열쇠는 그대로라, 잠그기 전의 meta.db 사본(백업·섀도 복사본)과 저장소 열쇠가 함께 있으면 그때 내용은 열린다. 저장소 열쇠를 가진 사람(이 PC 계정·클라우드 비밀번호)은 PIN을 오프라인으로 맞혀 볼 수 있어(Argon2id로 한 번 약 0.3초) PIN은 길게 정해야 한다. 예전 판의 meta.db 줄로 되돌리는 것(롤백)은 막지 않는다. 2.1 평문을 옮긴 뒤 원본은 지우기만 하므로(덮어쓰지 않음) 필요하면 `cipher /w`로 빈 공간을 지운다.
- 저장소 열쇠는 평소 그 PC의 Windows 계정 사본으로 자동으로 열린다. 새 PC·Windows를 다시 깔았으면 그 PC에서 비밀번호(또는 복구 코드)를 한 번 넣는다. 잊으면 리셋(모두 지움)뿐이다.
- 잠긴 폴더(§14)는 그 아래 meta를 그 폴더 열쇠로 다시 잠근다(파일 내용은 다시 쓰지 않는다). 그래서 잠그기·풀기가 바로 끝나고 목록의 `state`는 늘 `locked`다(`locking`·`unlocking`·`stalled`는 2.2 허브에서 생기지 않는다).

### 17.2 상태
- hello `caps`에 `"store"`. 클라우드가 켜졌지만 저장소가 열리지 않았으면 `"cloud":false`와 함께 `"store":"new"|"locked"|"missing"`(아직 안 만듦·비밀번호 필요·폴더나 드라이브 없음)을 준다. 열려 있으면 `"store":"open"`.
- 그때 클라우드 요청은 `store_locked`(new·locked) 또는 `store_missing`으로 거부한다. 앱은 "그 PC에서 클라우드를 열어야 함"을 보인다. 폰에서는 비밀번호를 넣지 않는다(허브 PC에서만).

### 17.3 cloud_get 넓히기
- `"length":<정수>`: offset부터 그만큼만 보낸다(영상 건너뛰기, 사진 화면용). 첫 프레임의 `size`는 늘 그 객체 전체 크기다. 받을 것이 없으면(`length:0`) 빈 `last=1` 데이터 프레임 하나.
- `"variant":"thumb"|"screen"|"poster"|"play"`: 원본 대신 허브가 만든 딸린 버전(§17.4). 없으면 `not_found`. `size`·`mtime` 검사(§12.2)는 그 버전 기준이다.

### 17.4 딸린 버전
- `cloud_list`·`cloud_search` 항목에 `"variants":["poster","play","thumb",...]`(있는 것만, 이름순)을 더한다. 허브는 사진·영상이 들어오면 뒤에서 만든다(몇 초–몇 분 뒤에 생긴다).
- `thumb`: JPEG, 긴 변 512. `cloud_thumb`(§15)은 이것을 줄여 준다(영상도 이제 미리보기가 있다).
- `screen`: 사진의 화면용 JPEG, 긴 변 2048. 원본이 작으면 없다(원본을 쓴다). 라이트박스는 이것을 먼저 열고, 100 %보다 크게 확대할 때만 원본을 받는다.
- `poster`: 영상의 첫 장면 JPEG, 긴 변 1280 이하.
- `play`: 영상의 재생용 버전. MPEG-TS, H.264(짧은 변 720, 약 2.5 Mbps) + AAC 128k. 원본이 이미 가벼운 H.264(짧은 변 720 이하, 4 Mbps 이하)면 없다(원본을 재생한다). TS라서 범위 요청(§17.3)으로 건너뛰며 재생할 수 있다.
- 잠긴 폴더 안의 것도 같다(딸린 버전의 열쇠도 그 폴더 열쇠로 잠긴 meta에 있다). 평문은 허브 디스크에 쓰지 않는다.

### 17.5 2.2 허브에서 달라지는 것
- `cloud_del`: 잠긴 폴더 밖은 허브의 휴지통으로 간다(30일 뒤 영구 삭제, 허브 PC 앱에서 되돌림). 잠긴 폴더 안은 바로 영구 삭제. 잠긴 폴더를 품은 폴더는 지우지 않는다(`bad_path`).
- `cloud_move`(§16): 잠긴 폴더 자체도 저장소 안 어디로든 옮길 수 있다(열쇠 없이, 안은 그대로 잠김). 잠긴 폴더 안팎을 오가는 것은 여전히 `vault_move`.
- 이름은 한 폴더 안에서 대소문자를 가리지 않고 겹치지 않는다(`a.txt`가 있으면 `A.TXT`는 `A (1).TXT`).
- "받은 파일도 클라우드에 모으기"로 받은 대화방 파일도 저장소 맨 위에 암호화돼 들어간다.
- 받을 자리를 정한 뒤 그 폴더가 잠기거나 풀리면 받기를 시작·마무리하지 않는다(`vault_busy`, 보내는 쪽이 다시 묻는다). 휴지통에서 되돌릴 때 원래 폴더의 열쇠가 바뀌었으면 맨 위로 되돌린다.
- 2.1까지의 평문 클라우드 폴더와 예전 잠긴 폴더는 허브 PC 앱이 저장소를 만들 때 옮긴다(예전 잠긴 폴더는 PIN을 한 번 넣어야 하고 새 복구 코드가 생긴다).

### 17.6 오류 코드 추가
| code | 뜻 |
|---|---|
| `store_locked` | 허브의 저장소가 아직 열리지 않았다(만들기 전이거나 비밀번호가 필요) |
| `store_missing` | 허브의 저장소 폴더·드라이브를 찾을 수 없다 |
| `store_password` | (허브 화면용) 클라우드 비밀번호·복구 코드가 틀렸다 |
| `store_exists` | (허브 화면용) 그 폴더에 이미 저장소가 있다 |
| `store_state` | (허브 화면용) 저장소를 알아볼 수 없다 |
| `storage` | 저장소의 암호문이 손상되었거나 바뀌었다 |
| `exists` | 같은 이름이 이미 있다 |
| `too_large` | (화면용) 너무 커서 원본을 메모리로 열지 않았다 |

## 18. 2.2.1 추가 (PC 허브)
### 18.1 잠긴 폴더 사이로 옮기기
허브 `caps`에 `"move2"`가 있으면 `cloud_move`(§16)가 잠긴 폴더 안팎·잠긴 폴더 사이로도 옮긴다(`vault_move`는 잠긴 폴더를 다른 잠긴 폴더 안에 넣을 때만). 허브는 그 항목과 아래 줄의 meta만 도착 자리의 열쇠로 다시 잠그고 파일 내용은 그대로 둔다(바로 끝남). 출발이 잠긴 폴더 안이면 그 열쇠도 있어야 하므로 헤더에 `"tokens":["<32 hex>", ...]`(최대 16개)를 더한다. 허브는 `token`과 `tokens` 중 맞는 것을 쓴다(§14.2의 다른 요청도 같다). 옮긴 잠긴 폴더의 열쇠는 앱이 새 자리로 옮겨 기억한다.

### 18.2 여러 개 이름 바꾸기
`caps`에 `"rename"`. `cloud_rename`: `{"items":[{"path":"<파일 또는 폴더>","name":"<새 이름>"}, ...]}`(1–200개, + 필요한 `token`·`tokens`) → `{"ok":true,"renamed":[{"path","name"}],"failed":[{"path","code"}]}`.
- 새 이름은 §12.1 조각 규칙을 지켜야 하고(아니면 그 항목 `bad_name`), 같은 폴더에 대소문자만 다른 것까지 같은 이름이 있으면 `exists`(번호를 붙이지 않는다). 같은 요청 안에서 서로 이름을 바꾸는 것(a→b, b→a)도 앞에서부터 차례로 처리하므로 `exists`가 될 수 있다.
- 잠긴 폴더 자체의 이름도 바꿀 수 있다(열쇠 없이). 잠긴 폴더 안은 열쇠가 있어야 한다.

### 18.3 강한 잠금(허브 PC 설정)
허브 PC에서 "강한 잠금"을 켜면 이 PC의 Windows 계정으로 자동으로 여는 사본을 지운다. 저장소 열쇠는 클라우드 비밀번호를 넣었을 때만 허브의 메모리에 있다. 허브 앱을 켤 때, Windows가 잠길 때, 정한 시간 동안 쓰지 않을 때 다시 잠긴다(hello `"store":"locked"`).
- `caps`에 `"store_unlock"`. `store_unlock`: `{"password":"<클라우드 비밀번호>"}` → `{"ok":true}`. 틀리면 `store_password`. 기기마다 따로 세어 5번 틀리면 60초, 그 뒤 두 배(최대 1시간) `vault_wait`(`retry`). 앱은 이 비밀번호를 저장하지 않는다.
- `store_lock`: 본문 없음 → 바로 잠근다(강한 잠금일 때만, 아니면 `store_state`).
- 강한 잠금이 켜진 허브는 hello 응답에 `"strong":true`를 함께 보낸다(앱은 이때만 "지금 잠그기"를 보인다, 2.2.1).

### 18.4 캡처 막기
PC 앱은 클라우드 안을 보여 주는 창(클라우드·라이트박스·재생·휴지통·PIN·비밀번호 창)을 화면 캡처·녹화·화면 공유에서 뺀다(`SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`). Android 앱은 그 화면에 `FLAG_SECURE`를 단다(캡처·녹화·최근 앱 미리보기에서 가려짐). 카메라로 화면을 찍는 것은 막을 수 없다.
