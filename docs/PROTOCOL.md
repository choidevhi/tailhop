# TailHop 프로토콜 v1

Tailscale 망 위에서 PC(Windows)와 폰(Android), 또는 PC와 PC가 텍스트·파일을 주고받는다.
PC ↔ PC는 PC 앱 1.4.0에서 더한 **v1 확장**이다. 선(wire) 형식·헤더 `v`는 그대로 1이고, 폰 쪽은 바뀐 것이 없다(§8).
**이중 잠금**: (1) Tailscale WireGuard 암호화 + 기기 인증, (2) 페어링으로 나눈 비밀키로 모든 메시지를 AES-256-GCM 암호화·인증.

## 1. 네트워크
- PC는 TCP `47100`, 폰은 TCP `47101`에서 대기한다. PC끼리는 서로 상대의 `47100`으로 보낸다.
- **자기 Tailscale IPv4(100.64.0.0/10)에만 bind** 한다. `0.0.0.0` 금지. 와이파이/LAN에서는 보이지 않는다.
- 접속 허용: 상대 IP가 페어링된 기기 IP와 같아야 한다. PC는 추가로 `tailscale whois --json <ip>`의 사용자 로그인이 PC 자신의 사용자와 같은지 확인한다.
  - 태그 노드(whois의 `Node.Tags`가 비어 있지 않음)는 PC가 페어링·메시지 모두 거부한다(1.5.0). 태그 노드는 사람 계정이 아니라 공용 "tagged-devices" 사용자로 묶여 UserID 비교로는 내 기기인지 알 수 없다. 이 PC 자신이 태그 노드면 다른 기기와 연결되지 않는다.
- 동시 접속 최대 4개, 소켓 무응답 30초면 끊는다.
  - (1.5.0) 연결을 받자마자, 슬롯을 잡기 전에 상대 IP가 페어링된 기기이거나 페어링 창이 열려 있는지 본다. 아니면 아무것도 읽지 않고 닫는다(whois도 돌리지 않음). Android는 처음부터 이 순서였다.
  - (1.5.0) PC는 인증 전(머리 22바이트, 페어링 첫 프레임) 무응답 한도를 5초로 줄이고, 인증(whois·페어링 키 첫 프레임)이 끝나면 30초로 늘린다.
- 수신 중지(PC·Android 1.5.0): 대기 소켓을 닫아 포트 자체를 닫는다(Android는 수신 서비스를 멈춘다). 보내는 쪽은 연결 거부·시간 초과를 받는다. 이미 연결된 받기는 끝까지 받고, 중지 중에도 보내기는 된다. PC는 중지 중에 페어링 창을 열지 않는다.

## 2. 키
- 장기 비밀 `S` (32바이트 난수, 페어링 때 폰이 생성).
- 방향 키: `K_dir = HKDF-SHA256(ikm=S, salt=32바이트 0, info, L=32)`
  - 폰→PC: info = `"tailhop v1 phone->pc"`
  - PC→폰: info = `"tailhop v1 pc->phone"`
  - 페어링: ikm = QR의 `P`, info = `"tailhop v1 pair"`
  - PC ↔ PC (§8): 코드를 보여 준 PC = host, 입력한 PC = joiner
    - joiner→host: info = `"tailhop v1 pc-joiner->pc-host"`
    - host→joiner: info = `"tailhop v1 pc-host->pc-joiner"`
  - 다섯 info가 모두 달라서 한 `S`에서 나온 키라도 방향·기기 종류가 다르면 절대 같은 키가 되지 않는다. 연결마다 새 salt로 세션 키를 만들고, 한 연결 안에서는 nonce의 `dir` 바이트로 두 방향을 나눈다.
- 저장: PC는 Windows DPAPI(CryptProtectData)로, 폰은 Android Keystore AES 키로 감싸서 저장한다. 평문 저장 금지. PC의 설정·페어링·기록 파일은 상속을 끊고 현재 사용자만 접근하는 ACL로 쓴다(1.5.0, ACL을 지원하지 않는 디스크면 기본 ACL 그대로).
- 확인 코드: `SHA-256(S)` 앞 4바이트를 big-endian 정수로 읽고 `% 1000000`, 6자리 0채움. 양쪽 화면에 표시.

## 3. 연결 형식 (보내는 쪽 = 클라이언트)
1. 평문 22바이트: `"THP1"`(4) + kind(1: `0x01` 페어링, `0x02` 메시지) + salt(16, 난수) + 예약 `0x00`(1)
2. 세션 키 `SK = HMAC-SHA256(key=K_dir, msg=salt)` (32바이트, AES-256 키)
3. 프레임: `len`(4바이트 big-endian, 암호문+태그 길이) + 암호문. `len`은 16 이상 `1048576+16` 이하. 벗어나면 즉시 끊는다.
4. nonce(12바이트) = `dir`(1) + `index`(10바이트 big-endian) + `last`(1)
   - `dir`: 클라이언트→서버 `0x00`, 서버→클라이언트 `0x01`
   - `index`: 방향별 0부터 1씩 증가
   - `last`: 마지막 프레임이면 `0x01`, 아니면 `0x00`
   - AAD: 22바이트 평문 머리 전체
5. 클라이언트 프레임 0 = 헤더 JSON(UTF-8), `last=0`. 프레임 1..n = 파일 데이터(평문 최대 1 MiB), **마지막 데이터 프레임은 `last=1`** (빈 평문 가능). 텍스트·페어링도 헤더 뒤에 빈 `last=1` 프레임 하나를 보낸다. `last=1`을 받기 전에 끊기면 전부 버린다.
6. 서버 응답: `dir=0x01, index=0, last=1` 프레임 하나, JSON `{"ok":true}` 또는 `{"ok":false,"error":"...","code":"..."}`.
   - `error`: 사람이 읽는 한국어 문장. 1.4 이하 PC·Android 1.3 이하가 화면에 그대로 띄우므로 화면 언어와 상관없이 늘 한국어로, 예전과 같은 문장을 보낸다.
   - `code`(1.5.0에서 더함, 없을 수 있음): 언어와 상관없는 고정 코드(`[a-z_]{1,40}`, §10). 받는 쪽은 아는 코드면 자기 화면 언어 문장으로 바꿔 보여 주고, 모르거나 없으면 `error`를 200자까지 그대로 보여 준다.
   - GCM 태그 검사에 실패하면 응답 없이 끊는다. 거부 응답을 보낸 쪽은 상대가 이미 보낸 프레임을 조금 읽어 버린 뒤 닫는다(안 읽은 데이터가 남은 채 닫으면 RST로 응답이 사라질 수 있다).

## 4. 헤더 JSON
공통: `{"v":1,"type":"text"|"file"|"pair"|"unpair","id":"<32자 hex 난수>","ts":<유닉스 ms>,"from":"<보낸 기기 이름>"}`
- `from`·응답 `name`은 받는 쪽이 제어문자와 bidi·폭 없는 문자(§5와 같은 목록)를 지우고 64자로 자른다.
- unpair (1.5.0, v1 확장, 폰 → PC): 본문 없이 헤더 뒤 빈 `last=1` 프레임 하나. 페어링 취소(§6). PC 1.5.0+는 그 기기의 페어링과 기록을 지운 뒤 `{"ok":true}`로 답한다. 이전 PC는 `unsupported`로 거부하며, 폰은 결과를 무시한다.
- text: `"text": "<문자열>"` (UTF-8 최대 1 MiB)
- file: `"name": "<파일명>"`, `"size": <바이트>` (최대 4 GiB)
- pair: `"secret": "<S base64url, 패딩 없음>"`, `"port": 47101` — 응답에 `"name": "<PC 이름>"`
  - PC가 페어링할 때만 `"device": "pc"`, `"port": <자기 대기 포트>`를 더 넣는다. `device`가 없으면 폰이다. `"phone"`/`"pc"` 외 값은 거부한다.

## 5. 받는 쪽 검사 (하나라도 실패하면 거부·삭제)
- 매직/kind/길이 검사, GCM 태그 검사(실패 즉시 끊음).
- `|ts - now| <= 300000ms`, 최근 10분 내 본 `id`면 거부(재전송 공격 방지, 디스크에 보관).
- 파일: 받은 바이트 수 == `size`(정수, bool 아님). `.part` 임시 파일을 배타적으로 만들어 받고 검증 후 이름 변경. 다른 수신이 같은 이름의 `.part`를 먼저 만들었으면 다음 번호를 쓰고, 실패해도 자기가 만든 `.part`만 지운다.
- 디스크 여유(1.5.0): 받기 전에 `size + 64 MiB`보다 남은 공간이 적으면 `disk_full`로 거부한다(PC는 저장 폴더의 디스크, Android는 공용 저장소).
- 파일명 정리: 경로 성분 제거(마지막 `/` `\` 뒤만), 다음 문자 → `_`: C0 제어문자, `0x7F–0x9F`, bidi·보이지 않는 문자(`U+061C`, `U+200B`, `U+200E–200F`, `U+202A–202E`, `U+2060–2064`, `U+2066–206F`, `U+FEFF`, 1.5.0), `<>:"/\|?*`. 앞의 `.`과 끝의 공백·`.` 제거, 최대 150자(확장자 유지), 비면 `file`. 첫 `.` 앞부분의 끝 공백을 뗀 값이 Windows 장치 이름(CON, PRN, AUX, NUL, CONIN$, CONOUT$, COM0–9, LPT0–9, COM¹²³, LPT¹²³, 대소문자 무관)이면 앞에 `_`(예: `COM1 .txt` → `_COM1 .txt`). 같은 이름이 있으면 `이름 (1).확장자`. 글자를 잇는 ZWJ/ZWNJ(`U+200C–200D`)는 그대로 둔다.
- 받은 파일은 절대 자동 실행하지 않는다.

## 6. 페어링
1. PC에서 "기기 연결" → `P` 32바이트 난수 생성, QR 표시(120초, 1회용):
   `tailhop://pair?v=1&h=<PC tailscale IP>&p=47100&n=<PC 이름, URL 인코딩>&k=<P base64url>`
2. 폰이 QR을 스캔 → `S` 생성 → kind `0x01`로 접속, 페어링 키로 암호화한 `type:"pair"` 헤더 전송.
3. PC: 페어링 창이 열려 있고, whois 사용자가 같고 태그 노드가 아니면 `S`, 폰 IP, 이름, 포트를 저장하고 창을 닫는다(`P` 폐기). `P`를 1회용으로 쓰는 순간 120초 마감을 다시 확인한다(받는 동안 지났으면 거부). `port`는 1–65535 정수(bool 아님). QR이 나중에 유출돼도 `S`는 모른다.
4. 양쪽에 확인 코드를 표시한다. 다시 페어링하면 이전 정보를 덮어쓴다.
5. (Android 1.5.0) 폰은 PC의 `ok` 응답을 받아도 **바로 저장하지 않는다.** QR만으로는 그 기기가 내 PC인지 알 수 없으므로(같은 tailnet의 다른 기기가 보여 준 QR일 수 있다) 확인 코드와 PC 이름·주소를 보여 주고 "PC에 표시된 코드와 같나요?"를 묻는다.
   - 같다: 그때 저장한다. 다른 기기가 이미 있으면 기본 공유 대상은 바꾸지 않는다(대화방을 열거나 공유 확인 창에서 고를 때만 바뀐다).
   - 다르다: `S`를 지우고, 그 `S`로 `type:"unpair"` 메시지(§4)를 보내 PC에도 지우게 한다(실패해도 폰은 저장하지 않았으므로 무시).
   - 선(wire) 형식은 그대로다. PC 쪽 동작(창·whois·저장)도 같다.

## 7. 테스트 벡터
`docs/test_vectors.json` 참고(같은 입력이면 양쪽 구현의 출력이 바이트 단위로 같아야 한다).

## 8. PC ↔ PC (v1 확장, PC 앱 1.4.0)
카메라가 없으므로 QR 대신 링크나 코드를 옮겨 적는다. 검사는 폰 페어링과 같고 더 줄인 것은 없다.
1. host PC가 "새 기기 연결"을 열면 폰용 QR과 함께 같은 창(같은 `P`, 120초, 1회용)의 두 형태를 보여 준다.
   - 링크: QR과 같은 `tailhop://pair?v=1&h=…&p=…&n=…&k=…` (매개변수를 더하지 않는다. 안드로이드 QR 검사가 그대로 통과하도록)
   - 짧은 코드: `<host IPv4>[:<port>]-XXXXX-XXXXX-…` — `P`(32바이트) + 검사 2바이트(`SHA-256("tailhop pair code|<host>:<port>|" + P)` 앞 2바이트)를 Crockford base32(`0-9A-Z`에서 I L O U 제외)로 적고 5글자씩 끊는다. 포트가 47100이면 생략. 대소문자·공백·하이픈 무관, `O→0`, `I/L→1`로 읽는다. 키 강도는 QR과 같은 256비트이고 검사 바이트는 오타(주소 포함)를 미리 잡는 용도다.
2. joiner PC는 입력을 엄격히 검사하고, host 주소가 Tailscale IPv4인지, `whois`로 같은 사용자의 기기인지, 자기 자신이 아닌지 **보내기 전에** 확인한다.
3. joiner가 `S`를 만들고 kind `0x01`로 접속해 `type:"pair"`, `device:"pc"`, `port`를 보낸다. host는 폰과 똑같이 창 열림·whois 같은 사용자·재전송·1회용을 검사하고, 추가로 자기 자신(같은 Tailscale 기기 ID)은 거부한다.
4. host는 상대를 `pc/host`로, joiner는 응답(인증된 `name`)을 받은 뒤 상대를 `pc/joiner`로 저장한다. 양쪽에 같은 확인 코드(§2)를 보여 준다. 다시 페어링하면 같은 기기(Tailscale 기기 ID)의 기존 정보를 덮어쓰며, 이때 역할이 바뀔 수 있다.
5. 메시지는 §3 그대로이며 방향 키만 §2의 PC ↔ PC info를 쓴다. 받는 쪽 검사(§1 IP·whois·기기 ID, §5)는 폰과 같다.

## 9. PC 저장 형식
`pairings.json` 항목: `ip`, `port`, `name`, `stable_id`, `kind`(`phone`|`pc`), `role`(폰은 `""`, PC는 `host`|`joiner`), `secret_dpapi`.
1.2 이하의 `phone_ip`/`phone_port`/`phone_name`/`phone_stable_id` 형식은 처음 읽을 때 `kind:"phone"`으로 옮긴다. 1.5.0 이전에 남기던 원본 사본 `pairings.json.v1.bak`(해제한 기기의 비밀까지 담김)은 새 형식을 제대로 읽으면 지운다. 기기 표시가 없는 예전 기록은 첫 폰의 대화로 옮겨 저장한다.
연결 해제(PC 1.5.0): 페어링과 함께 그 기기와 주고받은 기록(`texts/`의 긴 글 포함)도 지운다(Android와 같음). 받은 파일 자체는 지우지 않는다.

`settings.json`(1.5.0): `language`(`system`|`ko`|`en`|`ja`|`zh_CN`), `receiving`(기본 true), `pause_until`(유닉스 초, 시간을 정해 멈췄을 때만), `hotkey`(1.6.0, 전역 단축키를 켰을 때 true).

`bridge.json`(PC 1.6.0): 명령줄·탐색기 '보내기' 메뉴가 실행 중인 앱에 보내기를 맡기는 로컬 소켓(`127.0.0.1`)의 `port`, `token`(32바이트 hex), `pid`. 이 사용자만 읽는 ACL로 쓰고 앱이 끝나면 지운다. 요청은 JSON 한 줄(`token`, `paths`, `text`, `to`, `list`)이고 토큰이 틀리면 답하지 않는다. 기기 사이 선(wire) 형식과는 상관없다. 폴더는 `<폴더 이름>.zip`으로 묶어 보통 파일(§4 `file`)로 보낸다(링크는 따라가지 않는다).

기록(1.5.0): 2000자보다 긴 텍스트는 `texts/<32자 hex>.txt`에 따로 두고 `history.json` 항목에는 앞 2000자(`text`), 파일 이름(`text_file`), 전체 글자 수(`text_len`)만 남긴다. 1.4 이하 기록은 처음 열 때 한 번 옮긴다. 항목이 잘리거나 지워지면 그 파일도 지운다. Android는 같은 방식으로 `files/texts/<id>.txt`와 `tlen`을 쓴다.

## 10. 오류 코드 (응답의 `code`)
받는 쪽(응답을 보내는 쪽)이 쓰는 코드. 한국어 `error` 문장은 1.4와 같다.
| code | 뜻 |
|---|---|
| `no_body` | 헤더 뒤에 본문 프레임이 없다 |
| `bad_header` | 헤더 JSON을 읽을 수 없다 |
| `unsupported` | `v`·`type`을 지원하지 않는다 |
| `clock_skew` | `ts`가 ±5분을 벗어났다 |
| `bad_id` | `id` 형식이 잘못되었다 |
| `replay` | 최근 10분 안에 본 `id`다 |
| `bad_text` / `bad_text_format` | 텍스트가 잘못되었다 / 텍스트 뒤 프레임이 규칙과 다르다 |
| `bad_file_info` | `name`·`size`가 잘못되었다 |
| `file_too_big` / `file_incomplete` | 알린 크기보다 크다 / 덜 왔다 |
| `after_last` / `bad_frame_len` | 마지막 프레임 뒤 데이터 / 프레임 길이 위반 |
| `storage` / `storage_permission` / `storage_folder` / `storage_denied` | 저장 실패(PC도 1.5.0부터 `.part`를 만들 수 없을 때) / 저장 권한 없음(Android 8–9) / 저장 폴더를 만들 수 없음 / 저장소 접근 거부 |
| `disk_full` | (1.5.0) 받을 디스크 공간이 부족하다(§5) |

`tagged_node`(1.5.0)는 응답 코드가 아니라 화면용 코드다. PC는 태그 노드를 인증 전에 응답 없이 끊는다.
